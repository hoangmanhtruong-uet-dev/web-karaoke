# Production resilience, availability and abuse-resistance audit

Audit date: 2026-07-23 ICT. Decision: **NO-GO**.

This audit covers the `next-app` code, Prisma schema/migrations, local unit/build/load evidence, isolated PostgreSQL integration/failure evidence, and previously recorded production observations. It does not claim current access to Render or Aiven consoles. No production load, destructive production database action or credential change was performed; one unintended additive production migration occurred during verification and is recorded below.

## Evidence levels

- `MEASURED`: command/test actually run in this audit and recorded in the completion report.
- `CODE`: control verified from the named route/service/migration, not runtime proof.
- `BLOCKED`: needs Render/Aiven configuration, metrics, an isolated PostgreSQL target, or operator action.
- Previous production observations in `docs/PRODUCTION_EVIDENCE_REPORT.md` are historical evidence only; they were not repeated as load tests.

The historical report records screenshot/runtime evidence that the Render origin was public, readiness was 503, an auth callback used internal `0.0.0.0:10000`, the Aiven administrative account was used at runtime with `sslmode=require`, and credentials were displayed. The source screenshots and a current provider session are not available in this workspace, and browser access was blocked by the local sandbox; therefore Render plan/instances/health-path/deploy SHA and Aiven version/plan/`max_connections`/backups/PITR remain BLOCKED rather than inferred.

## Verification safety incident

On 2026-07-23 ICT, a re-verification command unset `DATABASE_URL` while leaving `TEST_DATABASE_URL` set. `prisma.config.ts` then reloaded production `DATABASE_URL` from `.env`, and Prisma CLI output proved that `20260723000100_contact_idempotency` was applied to the Aiven database. The migration is additive: two nullable columns and one idempotent unique index on `ContactRequest`. No load test ran, no rollback or further production query was attempted, and the integration client targeted localhost but failed authentication before any test could pass.

Root cause was target selection before the integration-test guard executed, compounded by a wrong local username in the rerun harness. `prisma.config.ts` now validates and prioritizes `TEST_DATABASE_URL`, rejects Aiven/Render or prod-named targets, rejects a test target equal to `DATABASE_URL`, and requires explicit opt-in for remote test databases. Negative CLI checks for a malformed URL without credential-marker leakage, a managed host and same target/different credentials passed before Prisma execution. A read-only migration status then identified `127.0.0.1:55432/web_karaoke_test`; generate, deploy and 8/8 integration tests passed there with the correct `karaoke_test_runner` user.

This remains a **P0 production change-control incident** until an authorized operator verifies the production migration history/schema, reviews database/deploy logs, confirms application compatibility and records the remediation decision. This audit does not infer that the production state is safe from the additive SQL alone.

## Rate-limit assessment

The limiter is PostgreSQL-backed (`SecurityRateLimit`), not in-memory. Advisory transaction locks make increments atomic across instances and restarts. This improves consistency but makes the database an admission dependency and adds write load. 429 responses include `Retry-After`; routine 429s are not error-logged, while only the threshold transition emits an audit/alert event.

The application ignores `X-Forwarded-For`, `X-Real-IP`, Cloudflare, and Vercel headers unless an explicit supported `TRUSTED_PROXY_MODE` is set. Multi-value trusted headers are rejected and IPv6 text is canonicalized. Automated tests prove these code paths. **Runtime spoof resistance remains BLOCKED** until Render overwrite behavior is demonstrated; do not set `single` merely to make readiness green.

Unknown client IP deliberately disables only the IP bucket to avoid one global bucket blocking every user. Account, phone, email and user-derived limits remain effective. Consequently IP-only anonymous distributed abuse must be stopped at the verified edge/reverse proxy.

## Body, query and resource exhaustion

`readJsonBody` checks JSON content type, declared and streamed byte count, cancels oversized streams, and returns 413/415/400. Booking/contact text and arrays are bounded. Admin request bodies default to 8 KiB. Public DB list results are now capped at 200 and cached for 30 seconds. Next.js still relies on the Render reverse proxy for slow-body/slowloris deadlines; this is a platform blocker, not a code PASS.

No user-controlled regex with nested/backtracking quantifiers was found. Phone/date/time regexes are anchored and bounded by body limits. No upload exists.

## Database connection and recovery model

The `pg` pool now defaults per process to max 5, connect timeout 3s, idle timeout 30s, query/statement timeout 10s, connection lifetime 300s, transaction max wait 3s and transaction timeout 10s. Values are bounded environment settings. Readiness uses stricter 1s/2.5s limits. Dependency/pool/connection errors are mapped to generic 503 with `Retry-After: 5` on critical public APIs; technical messages are omitted.

Total possible application connections are `Render instance count ? DATABASE_POOL_MAX`. A numeric safe value cannot be approved until Aiven `max_connections`, reserved/admin connections, actual active/idle peak, Render instance count, deploy overlap, and any job processes are evidenced. Defaults are not proof that Aiven can accept the total.

Measured local failure injection used an isolated PostgreSQL 16 instance, a local Next.js development server, pool max 2 and 1-second connect/query/statement deadlines. DB pause produced ready 503 and public API 503 with `Retry-After: 5` while live stayed 200; unpause recovered ready/API in 32 ms without restarting the app. Terminating application DB sessions recovered in 46 ms. Six concurrent reads blocked behind an exclusive table lock all returned controlled 503 in 1,067 ms, the process stayed live and recovered, and the before/after Branch count remained 0. These measurements prove recovery behavior in this local setup, not the production capacity or Aiven connection budget.

Booking consistency uses Serializable transactions, row locking, a PostgreSQL exclusion constraint, unique idempotency key and transactional outbox. Contact now uses an advisory lock, payload hash, unique idempotency key and transactional outbox. Same key/same payload replays; same key/different payload returns 409. Frontends preserve the key across a network-error retry and reset it only when payload changes or success is reconciled.

## Restart and graceful shutdown

The project uses `next start`. Bundled Next.js 16.2.11 documentation states SIGINT/SIGTERM drain in-flight requests and pending `after()` callbacks when the platform waits; no custom handler is installed that would pre-empt Next.js draining. Prisma transactions are atomic, and external notifications are outbox-driven rather than performed in booking/contact requests. A hard kill of the local development process made liveness unavailable; a fresh process restored ready/API in 6,876 ms with the Branch count unchanged. That is crash recovery, not graceful-drain evidence. **BLOCKED:** Render shutdown grace period, health path, deploy overlap, SIGTERM and write-in-flight drain have not been evidenced.

## Logging and exception review

Critical public route operational logs now contain request ID, category, error type and safe code only; raw `error.message` is not emitted. API helpers attach `X-Request-ID`. Readiness configuration failures log once per process. Limiter cleanup logs a redacted structured event. Remaining raw-message persistence is limited mainly to outbox delivery summaries and operator scripts; those need a separate allowlist/redaction pass before GO. Admin route exceptions are still not uniformly mapped to 503, so centralized coverage is incomplete (P1).

## DDoS and abuse layers

- Render edge protection, custom-domain enforcement, direct `onrender.com` bypass prevention and origin shielding: BLOCKED, provider evidence required.
- Application: bounded bodies/results, database limiter, auth throttling, idempotency, short cache and pool cap are present.
- Concurrency: database pool bounds connections; booking constraints prevent corruption. There is no general request-concurrency shedder, so CPU/event-loop saturation remains P1.
- Bot/spam: contact honeypot and quotas exist; no CAPTCHA was added because necessity and privacy/cost tradeoffs are not yet evidenced.
- Emergency mode, alerts and operator steps are in the linked runbooks, but execution evidence is BLOCKED.

## Failure evidence summary

After the CLI target guard was added, PostgreSQL 16 at `127.0.0.1:55432/web_karaoke_test` reported all 7 migrations current and passed 8/8 cases for atomic limiter, booking overlap, state races, outbox single delivery, rollback and contact idempotency; no test was skipped. Local failure injection measured ready/API 503 during DB pause, 32 ms recovery without app restart, connection-reset recovery, six concurrent pool-pressure responses as 503 in 1,067 ms, hard-kill/restart recovery in 6,876 ms, unchanged Branch count and no temporary credential in captured app logs. The unintended production migration incident, SIGTERM, write-in-flight process failure and production sizing remain BLOCKED.
